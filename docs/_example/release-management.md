# Release Management

## Цель

Описать единые правила подготовки, выпуска и сопровождения релизов.

---

## Version strategy

Для версионирования используем формат:

`MAJOR.MINOR.PATCH`

Где:

- `MAJOR` — номер суперспринта;
- `MINOR` — номер релиза внутри суперспринта;
- `PATCH` — номер hotfix / срочного исправления внутри релиза.

Примеры:

- `1.0.0` — первый релиз первого суперспринта;
- `1.1.0` — второй релиз первого суперспринта;
- `1.1.1` — первый hotfix для релиза `1.1.0`;
- `2.0.0` — первый релиз второго суперспринта.

---

## Release branches

Release-ветка создаётся от `develop`, когда команда готова начать стабилизацию релиза.

Формат ветки:

`release/vMAJOR.MINOR.PATCH`

Пример:

`release/v1.1.0`

В `release/*` разрешены:

- bugfix;
- исправления конфигурации;
- обновление версии;
- документация, связанная с релизом;
- изменения, необходимые для стабилизации релиза.

В `release/*` запрещены:

- новые feature-задачи;
- крупный рефакторинг;
- изменения, не связанные с подготовкой конкретного релиза.

---

## Перед выпуском релиза необходимо:

- убедиться, что все необходимые задачи влиты в `develop`;
- создать `release/*` от актуального `develop`;
- обновить версию приложения;
- собрать приложение;
- пройти минимальные проверки;
- исправить найденные дефекты в `release/*`;
- убедиться, что релизная ветка готова к merge в `main`.

---

## Когда релиз готов:

1. `release/*` мержится в `main` с tag(`v1.1.0`) с номером версии;
2. выполняется deploy в production;
3. `release/*` мержится обратно в `develop`, если в процессе стабилизации были исправления.

---

## Bugfix process

Используется для исправления ошибок при стабилизации релиза

Bugfix создается от `release/*`

Формат ветки: `bugfix/SRHR-XXXX`

Bugfix мержится обратно в `release/*`

---

## Hotfix process

Hotfix используется только для срочных исправлений production.

Hotfix-ветка создаётся от `main`.

Формат ветки:

`hotfix/vMAJOR.MINOR.PATCH`

Пример:

`hotfix/v1.1.1`

После завершения hotfix:

1. `hotfix/*` мержится в `main` создаётся новый tag;
2. выполняется deploy в production;
3. изменения обязательно возвращаются в `develop`;
4. при необходимости изменения также возвращаются в активную `release/*`.

---

## Release documentation

Для каждого релиза создаётся отдельная страница:

`releases/vMAJOR.MINOR.PATCH.md`


---

## Release checklist

Перед выпуском проверить:

- [ ] версия приложения обновлена;
- [ ] MR в `main` создан из правильной `release/*` ветки;
- [ ] build зелёный;
- [ ] критичные проверки пройдены;
- [ ] changelog / release notes обновлены, если используются;
- [ ] tag создан;
- [ ] изменения из `release/*` возвращены в `develop`;
- [ ] команда уведомлена о выпуске.

---

## Rollback

Если после релиза обнаружена критичная проблема, команда принимает одно из решений:

- откатить deploy на предыдущую стабильную версию;
- выпустить срочный hotfix;

Решение принимает ответственный за релиз совместно с командой.
