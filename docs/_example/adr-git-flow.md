## Рассматриваемые варианты

### 1. Git Flow (классический)

**Автор:** Vincent Driessen, 2010 ([оригинальная статья](https://nvie.com/posts/a-successful-git-branching-model/))

#### Структура

```
hotfix/*   -------------------------------------------------------*---*-------------------
                                                                 /     \
main       ---*-----------------------------------*-------------*-------*-----------------
              |                                   | (tag v1.0.0)        |\
develop    ---*---*-------*--*--------------------*-----------------------*---------------
                   \     /    \                  /                      |
feature/*  ---------*---*-----------------------------------------------------------------
                                \              /                        |
release/*  ----------------------*--*------*--*prod---------------------*(prodv1.0.1)-----
                                     \    /
bugfix/*   ---------------------------*--*------------------------------------------------

```

**Ветки:**
- `main` — стабильная production-версия;
- `develop` — основная ветка разработки;
- `feature/*` — ветки для новых задач;
- `release/*` — ветки подготовки релиза;
- `hotfix/*` — ветки срочных исправлений production;
- `bugfix/*` — ветки исправления ошибок в рамках текущей разработки.

#### `main`
Production-ветка. В этой ветке находится только стабильный код, который уже был выпущен или готов к выпуску в production.

Правила:
- прямые коммиты запрещены;
- изменения попадают только через merge из `release/*` или `hotfix/*`;
- каждый production-релиз должен быть отмечен тегом (v1.0.0).

#### `develop`
Основная ветка разработки. В эту ветку попадают завершённые задачи, которые должны войти в следующий релиз.

Правила:
- прямые коммиты нежелательны или запрещены;
- изменения попадают через Merge Request;
- от этой ветки создаются feature/* и release/*;
- ветка должна быть работоспособной и проходить тесты.

#### `feature/*`
Ветки для разработки новых функциональностей. Создаются от develop и мержатся обратно в develop

Правила:
- одна ветка — одна задача;
- после завершения создаётся Pull Request в develop;
- после merge ветка удаляется.

#### `release/*`
Ветки подготовки релиза. Создаются от develop мержатся в develop и main

Назначение:
- финальное тестирование;
- исправление найденных дефектов;
- обновление версии приложения;
- стабилизация релиза.

Правила:
- новая функциональность в release/* не добавляется;
- допускаются только bugfix, документация, конфигурация и подготовка релиза;
- после merge в main создаётся git tag.

#### `bugfix/*`
Ветки исправления ошибок в рамках текущей разработки или в рамках подготовки релиза.
Создаются от:

- `develop` — если ошибка найдена в рамках текущей разработки;
- `release/*` — если ошибка найдена во время стабилизации конкретного релиза.

Мержатся обратно в ту ветку, от которой были созданы:

#### `hotfix/*`
Ветки срочных исправлений production. Создаются от main мержатся в develop и main

Правила:
- используется только для production-инцидентов;
- после merge в master/main создаётся новый tag;
- исправление обязательно должно попасть обратно в develop.

#### Плюсы

- **Чёткое разделение** prod-кода и разработки
- **Явная фаза стабилизации** перед релизом через `release/*`
- **Параллельная поддержка** разных версий продукта
- **Hotfix не блокирует** текущую разработку
- **Подходит для версионируемых продуктов**

#### Минусы

- **Сложность процесса** — много типов веток, нужно учиться
- **Overhead на back-merge** из `main` в `develop`
- **Долгоживущие ветки расходятся** — больше merge-конфликтов
- **Плохо подходит для Continuous Deployment** — мешает явный шаг релиза

#### Когда использовать

- Релизы по расписанию (раз в спринт, месяц, квартал)
- Несколько активных версий продукта
- Требование формального release process

### 2. GitHub Flow

**Автор:** GitHub, ~2011 ([описание](https://docs.github.com/en/get-started/quickstart/github-flow))

#### Структура

```
main       ----*-------*---*-------*---*-------*---*-------*---(всегда деплоится)
                \     /     \     /     \     /     \     /
feature/*  ------*---*-------*---*-------*---*-------*---*-----
```

**Ветки:**
- `main` — всегда production-ready, деплоится автоматически
- `feature/*` — любая работа, мержится в `main` через PR

**Цикл:** ветка → коммиты → MR → ревью → merge в `main` → автодеплой.

#### Плюсы

- Простота — нечего объяснять новичкам
- Идеален для CI/CD и continuous deployment
- Быстрая обратная связь — изменения в продакшене за минуты
- Минимум merge-конфликтов при коротких feature-ветках
- Меньше overhead — нет release/hotfix процессов

#### Минусы

- Плохо подходит для сложного release management.
- Нет фазы стабилизации — баги ловятся уже в проде
- Сложно поддерживать несколько версий одновременно
- Требует зрелого CI/CD — без авто-тестов это путь к катастрофе

#### Когда использовать

- SaaS и веб-сервисы
- Команды с зрелым CI/CD
- Стартапы с быстрыми итерациями
- Продукт с одной production-версией

### 3. GitLab Flow

**Автор:** GitLab ([описание](https://docs.gitlab.com/ee/topics/gitlab_flow.html))

GitLab Flow — это модель ветвления, в которой основная разработка ведётся через `main`, а доставка изменений может быть организована через отдельные ветки окружений или release-ветки.

Общая структура:

```
feature/* → Merge Request → main → environment / release → production
```

**Идея:** GitHub Flow + дополнительные долгоживущие ветки для каждого окружения (`pre-production`, `production`) или для каждой версии (`2-3-stable`, `2-4-stable`).

**Цикл:** feature → `main` → `pre-production` → `production`. Изменения "стекают вниз" по веткам.


#### Основные варианты GitLab Flow
GitLab Flow может использоваться в нескольких вариантах:
- GitLab Flow with Environment Branches
- GitLab Flow with Release Branches

Изменения проходят путь:

##### Вариант - GitLab Flow with Environment Branches
```
main → feature/* → main → pre-production → production
```
- `feature/*` создаётся от `main`.
- После завершения задачи создаётся Merge Request в `main`.
- После merge в `main` изменения могут быть задеплоены на dev / test окружение.
- Когда `main` готова к поставке, изменения мержатся в `pre-production`.
- После проверки на `pre-production` изменения мержатся в `production`.
- Ветка `production` отражает состояние production-окружения.

##### Вариант - GitLab Flow with Release Branches
Этот вариант подходит, если команда выпускает версии продукта и поддерживает несколько релизов параллельно.
```
main → feature/* → main → release/*
```

- `feature/*` создаётся от `main`.
- После завершения задачи создаётся Merge Request в `main`.
- `release/*` создается от main

#### Плюсы

- **Чёткое соответствие** веток окружениям
- **Проще, чем Git Flow**, гибче, чем GitHub Flow
- **Возможность hotfix-а через cherry-pick** в более старые ветки
- **Хорошо для multi-environment deployment** (dev → staging → prod)
- **Поддержка нескольких версий** через release-ветки

#### Минусы

- **Cherry-pick между ветками** легко делать криво
- **Расхождение env-веток** при долгой задержке между деплоями
- **Менее формализован** — много вариаций
- **Требует дисциплины** в порядке мержа

#### Когда использовать

- Несколько окружений с разными политиками деплоя
- Команда хочет средний путь между Git Flow и GitHub Flow
- Длинная цепочка staging-окружений
- Поддержка нескольких major-версий

### 4. Trunk-Based Development (TBD)

**Автор:** Paul Hammant и др. ([trunkbaseddevelopment.com](https://trunkbaseddevelopment.com/))

#### Структура

```text
main        ----*-------*---*-------*---*-------*---*-------*--->  всегда готова к деплою
                 \     /     \     /     \     /     \     /
feature/*   ------*---*-------*---*-------*---*-------*---*-----

release/*   ----------------------------------------------------> для релизов опционально
```

**Идея:**
- `main` — единственная основная ветка разработки.
- `main` всегда должна быть стабильной.
- Изменения вливаются в `main` часто и маленькими порциями.
- Feature-ветки допускаются, но они должны быть короткоживущими.
- Долгоживущие ветки не приветствуются.
- Незавершённая функциональность прячется за feature flags.
- Релизиться можно из `main` в любой момент.

**Цикл:** короткая ветка (или прямой commit) → быстрое ревью → merge в `main` несколько раз в день.

Релиз может быть:

- автоматическим после merge в `main`
- ручным запуском pipeline из `main`
- через tag от конкретного commit в `main`
- через Docker image, собранный из commit SHA

#### Плюсы

- Минимум merge-конфликтов — все на одной ветке
- Высокая скорость поставки

#### Минусы

- Требует feature flags — без них нельзя
- Требует зрелого CI/CD и быстрых тестов (< 10 минут)
- Требует культурной зрелости команды
- Сложно для новичков — пугающее ощущение "всё в одну ветку"
- Тесты должны быть очень надёжными — красный билд блокирует всех

#### Когда использовать

- Большие команды на одной кодовой базе
- Зрелая CI/CD инфраструктура
- Микросервисы с независимым деплоем
- Команды с практикой continuous integration в полном смысле
- Когда merge-конфликты стали проблемой


## Naming convention для веток


Для названия веток используем единый формат:

```text
<type>/<SRHR-NUMBER>
```

#### Основные правила

- `feature/` - используется для новой функциональности. Создаем из `develop`, мерджим в `develop`
- `bugfix/` - используется для исправления ошибок, которые не являются срочным production hotfix. Создаем из `develop`/`release/*`, мерджим в `develop`/`release/*`
- `hotfix` - используется только для срочных исправлений production. Создаем из `main`, мерджим в `main` и `develop`
- `release` - используется для подготовки конкретной версии к выпуску. Создаем из `develop`, мерджим в `develop` и `main` с тегом


## Формат commit messages

- Произвольный

- Фиксированный

Структура:
```
<type>:(<task>) - <description>

feat:(SRHR-1111) - add audit
```

Разрешённые типы: `feat`, `fix`, `docs`, `refactor`, `test`, `build`, `revert`.

## Стратегия merge

1.  **Sync:** Перед созданием ветки обнови `develop` (`git pull origin develop`).
2.  **Branch:** Создай ветку `feature/...`.
3.  **Work:** Пишим код.
4.  **Test:** Запусти `./gradlew test` и `./gradlew detekt`.
5.  **Push & MR:** Merge Request.
6.  **Review Fix:**
7.  **Clean History (Squash & Amend)**
8.  **Merge**

### Что такое git commit --amend
Amend (Дополнить) — это способ переписать самый последний коммит.
* Сценарий: Ты сделал коммит, но забыл добавить один файл, или допустил опечатку в сообщении коммита.
* Правило: Можно делать только если ты еще не запушил коммит (или если это твоя личная ветка, и ты готов сделать force push).

Как сделать в IntelliJ IDEA:
* Открой окно Commit.
* Внеси нужные изменения.
* Поставь галочку Amend.
* Старое сообщение коммита подтянется автоматически. Исправь его если нужно.
* Нажми Commit.
* Если уже был пуш в ветку, то надо делать push force

### Что такое Squash
Squash — это объединение нескольких коммитов в один.

Как сделать в IntelliJ IDEA (Interactive Rebase):\
Это самый мощный способ. Мы переписываем историю ветки локально перед тем, как отдать её на ревью или смерджить.
* Перейди на вкладку Git (внизу) -> Log.
* Найди в списке коммитов тот, от которого началась твоя ветка (например, последний коммит из develop).
* Нажми на него Правой Кнопкой Мыши -> Interactively Rebase from Here...
* Откроется окно:
* Оставь верхний коммит как Pick (это будет "голова" нового объединенного коммита).
* Все остальные коммиты ниже пометь как Squash (они вольются в верхний).
* Нажми Start Rebase.
* IDEA предложит объединить сообщения всех коммитов. Удали мусор, напиши одно красивое сообщение.

Squash через git:
* git rebase develop
* git rebase -i develop
* в файле все pick кроме верхнего поменять на s (squash)
* сохранить файл (в Vim это :wq и Enter).
* Сразу после этого откроется новое окно редактора. Git предложит тебе объединить сообщения всех коммитов.
* Удали лишний мусор и оставь одно красивое сообщение.
* Сохранить и закрыть файл.
* git push --force


## Code Review процесс

**Минимальные требования к MR:**

- 2+ approve для `feature`/`bugfix` в `develop`
- 1+ approve для `release`/`hotfix` в `main`
- зелёный CI: lint(сейчас нету), unit-tests(сейчас нету), build
- ссылка на тикет в описании / описание того, что было сделано.
