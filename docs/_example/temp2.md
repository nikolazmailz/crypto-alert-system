> **Решение:** на 3–4 спринта выбираем классический Git Flow как экспериментальную стратегию ветвления. После завершения периода команда пересматривает решение на основе фактических проблем, удобства процесса и качества релизов.


## Decision (Решение)

Команда принимает решение использовать **классический Git Flow** в качестве экспериментальной стратегии ветвления на период **3–4 спринтов**.

На время эксперимента базовая модель ветвления выглядит так:

- `main` — стабильная production-ветка;
- `develop` — основная ветка разработки;
- `feature/*` — ветки для новых задач;
- `release/*` — ветки подготовки релиза;
- `bugfix/*` — исправления ошибок в рамках разработки или стабилизации релиза;
- `hotfix/*` — срочные исправления production.

Цель эксперимента — проверить, поможет ли Git Flow решить текущие проблемы процесса:

- отделить разработку новых задач от подготовки релиза;
- сделать production-состояние кода прозрачным;
- формализовать работу с hotfix;
- снизить хаос при параллельной разработке и выпуске релизов;
- сделать release management более предсказуемым.

Через **3–4 спринта** команда должна пересмотреть решение и оценить:

- стало ли понятнее, откуда создаются ветки и куда они мержатся;
- уменьшилось ли количество конфликтов и спорных ситуаций при merge;
- стало ли проще готовить релиз;
- не стал ли процесс слишком тяжёлым для команды;
- достаточно ли текущего уровня CI/CD и тестов для поддержки выбранной модели.

По итогам пересмотра команда может:

- оставить классический Git Flow;
- упростить процесс;
- перейти на другой подход, например GitLab Flow или Trunk-Based Development;
- скорректировать правила для `release/*`, `hotfix/*`, `bugfix/*`.



## Consequences (Последствия)

### Положительные

- Появляется понятное разделение между production-кодом, текущей разработкой и подготовкой релиза.
- `main` становится источником правды о том, что находится в production или готово к production.
- `develop` становится общей интеграционной веткой для задач следующего релиза.
- `release/*` позволяет отдельно стабилизировать релиз без блокировки разработки новых задач.
- `hotfix/*` даёт понятный процесс для срочных исправлений production.
- Команде проще договориться, от какой ветки создавать задачу и куда её возвращать.
- Упрощается версионирование релизов и выпуск тегов.
- Подход хорошо подходит для команды, которой нужен управляемый release management, а не непрерывный деплой каждой задачи в production.
- Экспериментальный формат снижает риск: решение принимается не навсегда, а на ограниченный период с последующим пересмотром.

### Отрицательные

- Процесс становится сложнее, чем текущая неформальная модель или GitHub Flow.
- Команде нужно привыкнуть к новым правилам: `main`, `develop`, `feature/*`, `release/*`, `bugfix/*`, `hotfix/*`.
- Возможны merge-конфликты между `main`, `develop` и `release/*`, особенно если ветки живут долго.
- Появляется дополнительная дисциплина: hotfix обязательно нужно возвращать не только в `main`, но и в `develop`.
- Если команда будет продолжать добавлять новые feature-задачи напрямую в `release/*`, Git Flow потеряет смысл.
- Без нормального CI, автотестов и правил Code Review процесс может стать формальным и не дать ожидаемой пользы.
- Возможен overhead на поддержку веток, особенно если релизы маленькие и частые.
- Нужно явно договориться, кто отвечает за создание `release/*`, выпуск тегов и контроль merge-направлений.


#### Плюсы

- Чёткое разделение `main`, `develop`, `release/*`, `feature/*`, `bugfix/*` и `hotfix/*`.
- `main` всегда отражает стабильное production-состояние.
- Новая разработка продолжается в `develop`, пока релиз стабилизируется в `release/*`.
- Есть отдельная фаза стабилизации релиза.
- Hotfix можно выпустить из `main`, не затрагивая незавершённую разработку.
- Подходит для версионируемого продукта и плановых релизов.
- Упрощает понимание, какие изменения входят в конкретную версию.
- Хороший вариант для эксперимента, если команда хочет формализовать release management.

#### Минусы

- Процесс сложнее, чем GitHub Flow или Trunk-Based Development.
- Требует дисциплины: нельзя превращать `release/*` в ветку для новой разработки.
- При долгоживущих ветках растёт риск merge-конфликтов.
- Hotfix нужно не забывать возвращать обратно в `develop`.
- Требует договорённостей по ролям: кто создаёт релиз, кто мержит, кто ставит tag.
- Без CI/CD и минимального набора тестов часть преимуществ Git Flow не раскрывается.
