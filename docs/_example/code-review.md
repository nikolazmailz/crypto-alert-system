# Code Review Process

## Цель

Code Review нужен не только для поиска ошибок, но и для поддержания общего качества кода, единого стиля разработки и распространения
знаний внутри команды.

Code Review должен помогать команде:

- находить дефекты до попадания изменений в основную ветку;
- проверять бизнес-логику и техническое решение;
- поддерживать читаемость и сопровождаемость кода;
- делиться знаниями между разработчиками;
- не допускать попадания неподготовленных изменений в релиз.

---

## Общие правила

Все изменения в основные ветки должны попадать только через Merge Request.

Прямые коммиты в `main`, `develop` и `release/*` запрещены, кроме отдельно согласованных технических исключений.

Перед созданием Merge Request автор должен:

- убедиться, что задача завершена;
- проверить, что проект собирается;
- добавить или обновить тесты, если изменение затрагивает бизнес-логику (happy path);
- описать бизнес смысл в Merge Request;
- приложить ссылку на задачу.

---

## Назначение reviewers

После создания MR автор должен:

- отправить ссылку на MR в чат разработки;
- тегнуть двух reviewers (Денис, плюс кто последний вносил изменение в сервис);

Reviewer может поставить реакцию `глазки`, если берёт MR в просмотр.

---

## Приоритет Code Review

Code Review является частью разработки, а не второстепенной активностью.

MR разработчика берётся в review в приоритетном порядке, если нет более срочных задач:

- production-инцидент;
- срочный hotfix;
- критичный bug;
- блокирующая проблема на тестовом или production-окружении;
- срочная релизная активность.

---

## Количество approve

Минимальные требования:

- `feature/*` → `develop`: минимум 2 approve;
- `bugfix/*` → `develop`: минимум 2 approve;
- `bugfix/*` → `release/*`: минимум 1 approve;
- `release/*` → `main`: минимум 1 approve;
- `hotfix/*` → `main`: минимум 1 approve.

---

### Шаблон описания MR

```md
## Что сделано

Краткое описание изменений.

## Зачем сделано

Краткое описание бизнес-смысла задачи.

## Как проверено

- [ ] Локально
- [ ] Unit-тесты
- [ ] Integration-тесты
- [ ] Happy path
- [ ] Проверка на тестовом окружении

## Риски

Есть / нет. Если есть — описать.

## Ссылка на задачу

SRHR-XXXX
```

---

## Условия merge

MR можно мержить, если:

- получено необходимое количество approve;
- нет unresolved-комментариев;
- проект успешно собирается;
- выполнены минимальные проверки;
- MR соответствует правилам выбранной Git-стратегии;
- изменение вливается в правильную целевую ветку.

---

## Исключения

Для срочных production hotfix допускается упрощённый процесс review.

---

## Ответственность

Автор MR отвечает за:

- качество подготовленного изменения;
- описание MR;
- прохождение проверок;
- обработку замечаний;
- корректную целевую ветку.

Reviewer отвечает за:

- внимательное review;
- конструктивные замечания;
- проверку рисков;
- своевременную реакцию на MR.

Команда отвечает за то, чтобы Code Review не становился формальностью и не блокировал разработку без причины.
