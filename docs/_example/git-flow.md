# Git Flow

## Цель

Этот документ описывает правила работы с Git-ветками в команде.

На время эксперимента команда использует **классический Git Flow** как основную стратегию ветвления.

Git Flow нужен для того, чтобы:

- отделить production-код от текущей разработки;
- сделать процесс подготовки релиза более управляемым;
- иметь отдельную ветку для стабилизации релиза;
- формализовать процесс hotfix;
- понимать, какие изменения входят в конкретную версию.

Решение о выборе Git Flow, причины выбора, рассмотренные альтернативы и критерии пересмотра описаны в [ADR: Выбор стратегии ветвления Git](./adr/ADR-001-git-branching-strategy.md).

Этот документ описывает правила работы с Git-ветками в команде.

Документ нужен для того, чтобы:

- зафиксировать единый подход к созданию и merge веток;
- отделить production-код от текущей разработки;
- сделать процесс подготовки релиза более управляемым;
- формализовать работу с ветками feature/*, release/*, bugfix/* и hotfix/*;
- снизить количество спорных ситуаций при выборе исходной и целевой ветки;
- сделать состав релиза и production-состояние кода более прозрачными.
  git log --merges release/v1.0.0..release/v1.1.0 --oneline

## Branches

В команде используются следующие типы веток:

| Ветка | Назначение |
|---|---|
| `main` | стабильная production-ветка |
| `develop` | основная ветка разработки |
| `feature/*` | разработка новой функциональности |
| `release/*` | подготовка и стабилизация релиза |
| `bugfix/*` | исправление ошибок в разработке или релизной ветке |
| `hotfix/*` | срочное исправление production |

---

## main

`main` — это стабильная production-ветка.

В `main` должен находиться только код, который:

- уже выпущен в production;
- либо полностью готов к выпуску в production.

### Rules

- Прямые коммиты в `main` запрещены.
- Изменения попадают в `main` только через Merge Request.
- В `main` мержатся только:
  - `release/*`;
  - `hotfix/*`.
- Каждый production-релиз должен быть отмечен git tag.
- `main` не используется для ежедневной разработки.

### Example

```text
release/v1.1.0 → main → tag v1.1.0
hotfix/v1.1.1  → main → tag v1.1.1
```

---

## develop

`develop` — основная ветка разработки.

В неё попадают завершённые задачи, которые должны войти в один из следующих релизов.

### Rules

- Прямые коммиты в `develop` запрещены или нежелательны.
- Изменения попадают в `develop` через Merge Request.
- От `develop` создаются:
  - `feature/*`;
  - `release/*`;
  - `bugfix/*`, если ошибка найдена в рамках текущей разработки.
- `develop` должна быть работоспособной.
- Перед merge в `develop` должен проходить минимальный набор проверок.

### Example

```text
develop → feature/SRHR-1234 → develop
develop → bugfix/SRHR-1235  → develop
develop → release/v1.1.0
```

---

## feature/*

`feature/*` используется для разработки новой функциональности.

Feature-ветка создаётся от `develop` и мержится обратно в `develop`.

### Branch naming

```text
feature/SRHR-XXXX
```

Пример:

```text
feature/SRHR-1234
```

### Rules

- Одна feature-ветка — одна задача.
- Ветка создаётся от актуального `develop`.
- После завершения задачи создаётся Merge Request в `develop`.
- После merge feature-ветка удаляется.
- В `feature/*` не должны попадать unrelated-изменения, не относящиеся к задаче.

### Flow

```text
develop → feature/SRHR-1234 → develop
```

### Before creating MR

Перед созданием Merge Request автор должен:

- обновить ветку от `develop`;
- проверить, что проект собирается;
- проверить happy path;
- добавить или обновить тесты, если изменение затрагивает бизнес-логику;
- заполнить описание MR;
- приложить ссылку на задачу.

---

## release/*

`release/*` используется для подготовки и стабилизации конкретного релиза.

Release-ветка создаётся от `develop`, когда команда договорилась о составе релиза и готова начать стабилизацию.

### Branch naming

```text
release/vMAJOR.MINOR.PATCH
```

Пример:

```text
release/v1.1.0
```

### Rules

В `release/*` разрешены:

- исправление дефектов;
- изменения конфигурации, необходимые для релиза;
- обновление версии приложения;
- документация, связанная с релизом;
- минимальные изменения, необходимые для стабилизации.

В `release/*` запрещены:

- новые feature-задачи;
- крупный рефакторинг;
- изменения, не связанные с подготовкой конкретного релиза;
- экспериментальные изменения.

### Flow

```text
develop → release/v1.1.0 → main
                         → develop
```

Когда релиз готов:

1. `release/*` мержится в `main`;
2. создаётся git tag;
3. выполняется deploy в production;
4. `release/*` мержится обратно в `develop`, если в процессе стабилизации были изменения.

### Example

```text
develop → release/v1.1.0
release/v1.1.0 → main
tag v1.1.0
release/v1.1.0 → develop
```

---

## bugfix/*

`bugfix/*` используется для исправления ошибок, которые не являются срочным production-инцидентом.

Bugfix может создаваться от:

- `develop` — если ошибка найдена в рамках текущей разработки;
- `release/*` — если ошибка найдена во время стабилизации конкретного релиза.

### Branch naming

```text
bugfix/SRHR-XXXX
```

Пример:

```text
bugfix/SRHR-1234
```

### Merge rules

Bugfix мержится обратно в ту ветку, от которой был создан.

| Откуда создан bugfix | Куда мержится |
|---|---|
| `develop` | `develop` |
| `release/*` | `release/*` |

### Flow

```text
develop → bugfix/SRHR-1234 → develop
```

```text
release/v1.1.0 → bugfix/SRHR-1235 → release/v1.1.0
```

Если bugfix был сделан в `release/*`, после выпуска релиза изменения должны быть возвращены в `develop`.

### Rules

В `bugfix/*` разрешены:

- исправление дефекта;
- тесты на исправленный сценарий;
- минимальные изменения, необходимые для исправления.

В `bugfix/*` запрещены:

- новая функциональность;
- крупный рефакторинг;
- изменения, не связанные с дефектом.

---

## hotfix/*

`hotfix/*` используется только для срочных исправлений production.

Hotfix создаётся, когда ошибка уже находится в production и требует срочного исправления вне обычного релизного цикла.

### Branch naming

```text
hotfix/vMAJOR.MINOR.PATCH
```

Пример:

```text
hotfix/v1.1.1
```

### Rules

- Hotfix создаётся только от `main`.
- Hotfix мержится в `main`.
- После merge в `main` создаётся новый git tag.
- Исправление обязательно возвращается в `develop`.
- Если есть активная `release/*`, в которую тоже нужно внести исправление, hotfix должен быть перенесён и туда.

### Flow

```text
main → hotfix/v1.1.1 → main
                    → develop
```

### Example

```text
main → hotfix/v1.1.1
hotfix/v1.1.1 → main
tag v1.1.1
hotfix/v1.1.1 → develop
```

---

## Bugfix vs Hotfix

| Тип ветки | Когда используется | Откуда создаётся | Куда мержится |
|---|---|---|---|
| `bugfix/*` | Ошибка в разработке или на этапе стабилизации релиза | `develop` или `release/*` | обратно в исходную ветку |
| `hotfix/*` | Срочная ошибка в production | `main` | `main` и `develop` |

Главное правило:

> Если ошибка ещё не попала в production — используется `bugfix/*`.
> Если ошибка уже в production и требует срочного исправления — используется `hotfix/*`.

## Branch naming convention

Для названия веток используется единый формат:

```text
<type>/<task-or-version>
```

### Examples

```text
feature/SRHR-1234
bugfix/SRHR-1235
release/v1.1.0
hotfix/v1.1.1
```

### Allowed branch types

| Type | Example | Назначение |
|---|---|---|
| `feature` | `feature/SRHR-1234` | новая функциональность |
| `bugfix` | `bugfix/SRHR-1235` | исправление ошибки |
| `release` | `release/v1.1.0` | подготовка релиза |
| `hotfix` | `hotfix/v1.1.1` | срочное исправление production |

---

## Merge Request rules

Все изменения в основные ветки должны проходить через Merge Request.

### Required target branches

| Source branch | Target branch |
|---|---|
| `feature/*` | `develop` |
| `bugfix/*` from `develop` | `develop` |
| `bugfix/*` from `release/*` | соответствующая `release/*` |
| `release/*` | `main` и затем `develop` |
| `hotfix/*` | `main` и затем `develop` |

### Before merge

Перед merge необходимо проверить:

- MR создан в правильную целевую ветку;
- описание MR заполнено;
- есть ссылка на задачу;
- получено необходимое количество approve;
- build успешный;
- замечания reviewer обработаны;
- изменение соответствует типу ветки.

Подробные правила Code Review описаны в [Code Review Process](./code-review.md).

## Versioning

Для версионирования используется формат:

```text
MAJOR.MINOR.PATCH
```

Где:

- `MAJOR` — номер суперспринта;
- `MINOR` — номер релиза внутри суперспринта;
- `PATCH` — номер hotfix или срочного исправления внутри релиза.

### Examples

```text
v1.0.0
v1.1.0
v1.1.1
v2.0.0
```

Подробные правила версионирования, подготовки релиза, hotfix и git tag описаны в [Release Management](./release-management.md).

## Git tags

Git tag создаётся для каждой версии, выпущенной в production.

### Format

```text
vMAJOR.MINOR.PATCH
```

### Examples

```text
v1.0.0
v1.1.0
v1.1.1
```

Tag создаётся после merge в `main`.

## Common flows

### Feature flow

```text
develop
  └── feature/SRHR-1234
        └── MR → develop
```

Шаги:

1. Обновить `develop`.
2. Создать `feature/*` от `develop`.
3. Выполнить задачу.
4. Проверить изменения.
5. Создать MR в `develop`.
6. Пройти Code Review.
7. Смержить в `develop`.
8. Удалить feature-ветку.

---

### Release flow

```text
develop
  └── release/v1.1.0
        ├── bugfix/*
        └── MR → main → tag v1.1.0
        └── MR → develop
```

Шаги:

1. Убедиться, что все задачи релиза влиты в `develop`.
2. Создать `release/*` от `develop`.
3. Провести стабилизацию релиза.
4. Исправить найденные дефекты через `bugfix/*`.
5. Смержить `release/*` в `main`.
6. Создать tag.
7. Выполнить deploy.
8. Вернуть изменения из `release/*` в `develop`.

---

### Hotfix flow

```text
main
  └── hotfix/v1.1.1
        ├── MR → main → tag v1.1.1
        └── MR → develop
```

Шаги:

1. Создать `hotfix/*` от `main`.
2. Исправить production-дефект.
3. Проверить исправление.
4. Создать MR в `main`.
5. После merge создать tag.
6. Выполнить deploy.
7. Вернуть исправление в `develop`.
8. При необходимости перенести исправление в активную `release/*`.

---

## What is forbidden

Запрещено:

- делать прямые коммиты в `main`;
- делать прямые коммиты в `develop` без согласования;
- мержить `feature/*` напрямую в `main`;
- мержить новые feature-задачи в `release/*`;
- использовать `hotfix/*` для обычных bugfix;
- держать feature-ветки долгоживущими без необходимости;
- смешивать несколько несвязанных задач в одной ветке;
- выпускать production-релиз без tag;
- забывать возвращать hotfix в `develop`.

---

## Responsibility

Автор изменения отвечает за:

- создание ветки от правильной исходной ветки;
- актуальность своей ветки;
- корректную целевую ветку MR;
- описание MR;
- обработку замечаний reviewer;
- проверку happy path.

Reviewer отвечает за:

- проверку корректности решения;
- проверку рисков;
- проверку соответствия Git Flow;
- своевременную обратную связь.

Ответственный за релиз отвечает за:

- создание `release/*`;
- контроль состава релиза;
- merge `release/*` в `main`;
- создание tag;
- возврат изменений в `develop`;
- уведомление команды о выпуске.
